# EKS — Interview Questions

---

## Easy

### 1. What is Amazon EKS and what problem does it solve?

**Answer:**
Amazon Elastic Kubernetes Service (EKS) is a fully managed Kubernetes service that removes the operational burden of running the Kubernetes control plane. Without EKS, teams must manually install, configure, patch, upgrade, and maintain etcd, the API server, the scheduler, and controller manager nodes — all of which require deep Kubernetes expertise and significant operational overhead.

EKS solves this by:
- Running a highly available, multi-AZ control plane managed entirely by AWS
- Automatically patching and upgrading control plane components
- Integrating natively with AWS services (IAM, VPC, ALB, ECR, CloudWatch, etc.)
- Providing certified, upstream-compatible Kubernetes so workloads are fully portable

### 2. What is the difference between EKS Managed Node Groups and Self-Managed Nodes?

**Answer:**

| Feature | Managed Node Groups | Self-Managed Nodes |
|---|---|---|
| Node provisioning | AWS handles via EC2 Auto Scaling Groups | You provision and manage EC2 instances manually |
| AMI updates | AWS provides and can auto-update EKS-optimized AMIs | You manage AMI selection and updates |
| Node draining | AWS automatically drains nodes before termination | You must implement draining logic yourself |
| Lifecycle hooks | Integrated | Manual configuration required |
| Flexibility | Limited to supported configurations | Full control over instance configuration |

Managed Node Groups are recommended for most workloads because they reduce operational burden, while Self-Managed Nodes are used when you need specific kernel configurations, custom AMIs, or instance types not yet supported by managed groups.

### 3. What is a Kubernetes Pod and how does it relate to EKS?

**Answer:**
A Pod is the smallest deployable unit in Kubernetes — it represents one or more containers that share the same network namespace, storage volumes, and lifecycle. Containers within a Pod communicate via `localhost` and share an IP address.

In EKS:
- Pods run on EC2 worker nodes (or AWS Fargate)
- Each Pod gets a unique IP address from the VPC CIDR via the **AWS VPC CNI plugin** (amazon-vpc-cni-k8s)
- This means Pod IPs are routable directly within the VPC — no overlay network is required
- EKS manages the Kubernetes control plane that schedules and orchestrates Pods across your nodes

---

### 4. What is the AWS VPC CNI plugin and why is it important for EKS?

**Answer:**
The AWS VPC CNI (Container Network Interface) plugin is the default networking plugin for EKS. It assigns each Pod a real VPC IP address directly from the node's ENI (Elastic Network Interface).

**Why it matters:**
- **Native VPC routing:** Pod IPs are first-class VPC citizens — no overlay network or NAT required
- **Security Groups for Pods:** You can attach VPC Security Groups directly to individual Pods
- **Direct connectivity:** Pods can communicate with other AWS services, RDS, Lambda, etc., using their VPC IP
- **Performance:** Eliminates the overhead of encapsulation (VXLAN/GRE) used by other CNI plugins

**Limitation:** The number of Pods per node is limited by the number of IPs each EC2 instance type can support (ENIs × IPs per ENI).

### 5. What is `kubectl` and how do you configure it to work with EKS?

**Answer:**
`kubectl` is the Kubernetes command-line tool used to interact with any Kubernetes cluster, including EKS. It communicates with the Kubernetes API server.

**Configuring kubectl for EKS:**

```bash
# Update kubeconfig to add EKS cluster context
aws eks update-kubeconfig \
  --region us-east-1 \
  --name my-cluster \
  --profile my-aws-profile

# Verify connectivity
kubectl get nodes
kubectl get pods --all-namespaces
```

This command:
1. Calls the EKS API to retrieve cluster endpoint and certificate authority data
2. Writes a new context to `~/.kube/config`
3. Configures the `aws eks get-token` command as the credential provider (using IAM for authentication)

Authentication flow: `kubectl` → `aws eks get-token` → IAM → EKS API server → Kubernetes RBAC

## Medium

### 1. Explain how IAM authentication and Kubernetes RBAC work together in EKS.

**Answer:**
EKS uses a two-layer authorization model: **IAM for authentication** and **Kubernetes RBAC for authorization**.

**Authentication Layer (IAM):**
- When `kubectl` makes a request, it includes a bearer token generated by `aws eks get-token`
- This token is a pre-signed STS `GetCallerIdentity` URL, valid for 15 minutes
- The EKS API server uses the **AWS IAM Authenticator** webhook to validate this token against STS
- STS returns the IAM identity (User ARN or Role ARN)

**Authorization Layer (Kubernetes RBAC):**
- The IAM identity is mapped to a Kubernetes username/group via the `aws-auth` ConfigMap (legacy) or **EKS Access Entries** (new method)
- Kubernetes RBAC then evaluates ClusterRoleBindings and RoleBindings to determine what the identity is allowed to do

**Example `aws-auth` ConfigMap mapping:**
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: aws-auth
  namespace: kube-system
data:
  mapRoles: |
    - rolearn: arn:aws:iam::123456789012:role/NodeGroupRole
      username: system:node:{{EC2PrivateDNSName}}
      groups:
        - system:bootstrappers
        - system:nodes
    - rolearn: arn:aws:iam::123456789012:role/DevTeamRole
      username: dev-team
      groups:
        - dev-team-group
```

**EKS Access Entries (newer approach):**
```bash
aws eks create-access-entry \
  --cluster-name my-cluster \
  --principal-arn arn:aws:iam::123456789012:role/DevTeamRole \
  --type STANDARD

aws eks associate-access-policy \
  --cluster-name my-cluster \
  --principal-arn arn:aws:iam::123456789012:role/DevTeamRole \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSViewPolicy \
  --access-scope '{"type":"namespace","namespaces":["production"]}'
```

**Key gotcha:** The cluster creator's IAM identity is automatically granted `system:masters` access. If you use a CI/CD role to create the cluster, that role must be used (or mapped) for subsequent administration.

### 2. What is the EKS Pod Identity and how does it differ from IRSA (IAM Roles for Service Accounts)?

**Answer:**
Both mechanisms allow Pods to assume IAM roles without storing long-lived credentials, but they differ significantly in implementation.

**IRSA (IAM Roles for Service Accounts) — Older approach:**
- Uses OIDC federation between EKS and IAM
- Each cluster has an OIDC provider URL
- IAM Role trust policy scoped to the OIDC provider + service account
- JWT token projected into Pod at `/var/run/secrets/eks.amazonaws.com/serviceaccount/token`
- AWS SDK exchanges this JWT for temporary credentials via STS `AssumeRoleWithWebIdentity`

```json
// IAM Trust Policy for IRSA
{
  "Effect": "Allow",
  "Principal": {
    "Federated": "arn:aws:iam::123456789012:oidc-provider/oidc.eks.us-east-1.amazonaws.com/id/EXAMPLED539D4633E53DE1B71EXAMPLE"
  },
  "Action": "sts:AssumeRoleWithWebIdentity",
  "Condition": {
    "StringEquals": {
      "oidc.eks.us-east-1.amazonaws.com/id/EXAMPLED539D4633E53DE1B71EXAMPLE:sub": "system:serviceaccount:default:my-service-account"
    }
  }
}
```

**EKS Pod Identity — Newer approach (GA 2023):**
- Uses a new EKS Pod Identity Agent DaemonSet on nodes
- IAM trust policy uses `pods.eks.amazonaws.com` as the principal (no OIDC setup required)
- Association created directly between IAM role and Kubernetes service account via EKS API
- Credentials fetched from a local endpoint on the node (`169.254.170.23`)

```bash
# Create Pod Identity association
aws eks create-pod-identity-association \
  --cluster-name my-cluster \
  --namespace my-namespace \
  --service-account my-sa \
  --role-arn arn:aws:iam::123456789012:role/MyPodRole
```

**Comparison:**

| Feature | IRSA | EKS Pod Identity |
|---|---|---|
| OIDC setup required | Yes | No |
| Role portability across clusters | No (OIDC URL in trust policy) | Yes (same role, multiple clusters) |
| Credential refresh | On expiry | Automatic, more frequent |
| Audit trail | CloudTrail STS events | CloudTrail EKS events |
| Complexity | Higher | Lower |

**Recommendation:** Use EKS Pod Identity for new workloads; it's simpler and more portable.

### 3. How does the Kubernetes Cluster Autoscaler work with EKS, and what are its limitations compared to Karpenter?

**Answer:**

**Cluster Autoscaler (CA) with EKS:**
- CA monitors Pods in `Pending` state due to insufficient resources
- It identifies which Auto Scaling Group (ASG) can accommodate the pending Pod based on node group configuration
- Scales up the ASG by incrementing `DesiredCapacity`
- Scales down by identifying underutilized nodes, cordoning them, draining Pods, and terminating instances
- Requires `cluster-autoscaler` IAM permissions on the node or via IRSA

**Limitations of Cluster Autoscaler:**
1. **ASG-bound:** Each node group maps to one ASG with a fixed instance type — no instance type diversification within a group
2. **Slow scale-up:** Provisioning a new node can take 3–5 minutes
3. **Complex multi-group configuration:** Requires careful `priority-expander` configuration when multiple node groups exist
4. **Coarse-grained:** Cannot right-size nodes to the exact workload requirements
5. **Scale-down is conservative:** Default 10-minute delay before scale-down evaluation

**Karpenter — Modern Alternative:**
- Karpenter is an open-source, flexible, high-performance Kubernetes Node Autoscaler (now a CNCF project)
- Watches for unschedulable Pods and directly calls EC2 Fleet/Spot APIs — no ASG dependency
- Selects instance types dynamically based on Pod resource requirements and constraints
- Supports **consolidation**: actively replaces nodes to pack workloads more efficiently
- Typically provisions nodes in **~60 seconds** vs 3–5 minutes for CA

```yaml
# Karpenter NodePool example
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: default
spec:
  template:
    spec:
      requirements:
        - key: karpenter.sh/capacity-type
          operator: In
          values: ["spot", "on-demand"]
        - key: kubernetes.io/arch
          operator: In
          values: ["amd64", "arm64"]
        - key: karpenter.k8s.aws/instance-category
          operator: In
          values: ["c", "m", "r"]
      nodeClassRef:
        group: karpenter.k8s.aws
        kind: EC2NodeClass
        name: default
  limits:
    cpu: 1000
  disruption:
    consolidationPolicy: WhenUnderutilized
```

**When to use CA vs Karpenter:**
- **CA:** Simpler environments, strict instance type requirements, teams already invested in CA
- **Karpenter:** Cost optimization via Spot diversification, faster scale-up needs, complex heterogeneous workloads

### 4. Explain EKS Fargate and when you would choose it over EC2 node groups.

**Answer:**
EKS Fargate runs Kubernetes Pods on AWS-managed serverless compute — you never see or manage the underlying EC2 instances. Each Pod gets its own dedicated micro-VM (using Firecracker), providing strong workload isolation.

**How Fargate works with EKS:**
- You define **Fargate Profiles** that specify which Pods (by namespace and label selectors) run on Fargate
- When a matching Pod is created, EKS Fargate provisions a dedicated compute environment sized to the Pod's resource requests
- The Fargate node appears in `kubectl get nodes` but is not accessible via SSH

```yaml
# Fargate Profile via eksctl
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig
metadata:
  name: my-cluster
  region: us-east-1
fargateProfiles:
  - name: fp-default
    selectors:
      - namespace: default
      - namespace: kube-system
  - name: fp-production
    selectors:
      - namespace: production
        labels:
          workload-type: serverless
```

**Advantages of Fargate:**
- No node management, patching, or capacity planning
- Per-Pod billing (CPU/memory per second)
- Strong isolation — no noisy neighbor at the VM level
- Automatic right-sizing (no over-provisioning of node capacity)

**Limitations of Fargate:**
- **No DaemonSets:** Cannot run DaemonSet Pods (e.g., node-level agents like Datadog, Fluentd) — must use sidecars instead
- **No privileged containers:** No `hostNetwork`, `hostPID`, or privileged security contexts
- **No GPU support**
- **No persistent volumes** (except EFS — EBS is not supported)
- **Slower cold start:** Pod provisioning takes longer than scheduling to a warm node
- **Cost:** Can be more expensive than EC2 for sustained, predictable workloads
- **Limited instance sizing:** Pod size is rounded up to the nearest Fargate configuration

**Choose Fargate when:**
- Workloads are bursty or unpredictable
- Strong isolation between tenants is required
- You want zero node management overhead
- Running batch jobs or event-driven workloads

**Choose EC2 Node Groups when:**
- Running DaemonSets for observability or security agents
- Needing GPU, custom AMIs, or specific kernel configurations
- Cost-optimizing for sustained, predictable workloads
- Requiring high IOPS with EBS volumes

### 5. How do you implement network policies in EKS and what are the available options?

**Answer:**
By default, all Pods in a Kubernetes cluster can communicate with all other Pods — there is no network segmentation. Kubernetes NetworkPolicy resources define rules to restrict this traffic, but they require a CNI plugin that enforces them.

**Option 1: AWS VPC CNI with Network Policy Support (Recommended for EKS)**

Since EKS add-on version `v1.14.0+`, the VPC CNI includes built-in network policy enforcement using eBPF (via the `aws-node` DaemonSet and `aws-network-policy-agent`). No additional CNI plugin needed.

```bash
# Enable network policy on VPC CNI add-on
aws eks update-addon \
  --cluster-name my-cluster \
  --addon-name vpc-cni \
  --configuration-values '{"enableNetworkPolicy": "true"}'
```

**Option 2: Calico**

Calico is a popular third-party CNI that provides rich NetworkPolicy support. In EKS, you typically use Calico in **policy-only mode** (keeping VPC CNI for networking, adding Calico only for policy enforcement).

```bash
kubectl apply -f https://raw.githubusercontent.com/aws/amazon-vpc-cni-k8s/master/config/master/calico-operator.yaml
```

**NetworkPolicy Example:**
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-backend
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: backend
